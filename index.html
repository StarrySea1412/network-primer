01第一章

DNS：互联网的电话簿

浏览器不认识 example.com，只认识 93.184.216.34。把名字变成数字的，是递归解析器和它身后的一整条问路链。

先分清两个常被混用的词：递归查询是你对解析器说的——「我只要结果，跑腿的事你做」；迭代查询是解析器对根/TLD/权威说的——「告诉我下一步该问谁，我自己去」。一个替你跑腿，一个自己问路，二者拼成完整的解析链。

每条 DNS 记录都带着 TTL（生存时间），单位秒。TTL 是一把双刃剑：设 3600s，缓存命中率高、解析快，但网站换 IP 后全世界最长要记一小时旧地址；设 60s，切换灵活、解析量翻十倍。Cloudflare 免费版默认 300s，企业切换窗口前会把 TTL 预先降到 60——先降 TTL、等旧值过期、再切 IP、最后升回，这是运维切换 DNS 的标准四步。

02第二章

TCP：先握手，再说话

拿到 IP 之后，还不能直接要数据——要先和服务器握三次手，同步两边的「计数器」。计数器对上了，连接才算建立。

三次握手的本质是同步双方的初始序号（ISN）。序号是 TCP 可靠性的地基：每个字节都有编号，确认号 = 收到的最后一个字节 + 1。ISN 随机化还有安全意义——如果从 0 开始，攻击者可以预测序号伪造连接。

注意 MSS（最大段 1460B）在握手里就协商好了——它是 MTU 1500 减去 IP 头 20 和 TCP 头 20。之后的数据段谁也不会超过它，避免 IP 层分片。

「为什么不是两次」的经典追问值得完整论证：若只有两次，服务器发完 SYN+ACK 就认为连接建立并分配缓冲区——但这个包若在路上迟到，客户端早已放弃，服务器的缓冲区就被一个永远不会有数据的「幽灵连接」占着。三次握手的第三次 ACK 让客户端对服务器说一句收到，双方各确认一次对方的收发能力，缺一不可。四次则纯属冗余——SYN+ACK 本来就可以捎带。

还有个高并发服务器绕不开的名词：TIME_WAIT。主动关闭的一方在连接消失后要等 2MSL（Linux 60s）才释放端口——为了网络中迟到的旧包自然死亡。压测时「Cannot assign requested address」就是本机端口耗尽，解法是 tcp_tw_reuse 而不是暴力缩 MSL。

seq/ack 按真实语义递增（SYN 消耗一个序号）。注入丢包后：发送方等不到 ack，超时重传同一个报文；接收方收到重复报文会丢弃但仍重发 ack——这就是 TCP 可靠性的全部魔法。
为什么是三次不是两次：两次握手无法让服务器确认「客户端能收到自己说的话」。第三次 ACK 就是客户端在说「你刚才那句话我听到了」——缺少它，服务器的资源会被浪费在永远等不到回应的半连接上（经典 SYN Flood 攻击正是利用这一点）。
03第三章

滑动窗口与拥塞控制：TCP 的发动机

握手只是开机。真正决定「多快传完」的是两台发动机：滑动窗口决定一次发多少，拥塞控制决定窗口开多大——慢启动、AIMD、快恢复，全是真实算法。

两条铁律：①接收方有缓冲上限（流量控制，rwnd）；②网络有承载上限（拥塞控制，cwnd）。发送方每过一个 RTT 才能学到一次「网络受不受得了」——慢启动阶段每 RTT 窗口翻倍，撞上丢包后减半，再线性爬升。那条锯齿线，就是互联网上每一笔流量真实走过的形状。

「慢启动」这个名字是历史误称——它一点都不慢，是指数级的增长（1→2→4→8），慢的是「增长的速度会变慢」。真正慢的是 AIMD 阶段的线性 +1。这四个算法的进化史就是三十年互联网的编年史：Tahoe（1988，丢包即回1）→ Reno（加快恢复）→ CUBIC（2006，Linux 默认，用三次函数替代线性）→ BBR（2016，Google 闭门三年后开源——不看丢包看带宽时延积，Kubernetes 集群与 Google 全站部署后平均吞吐提升 4%，某些弱网线路提升 25 倍）。

锯齿还有一个容易被忽略的意义：它是共享网络的公平性机制。多条流挤同一条链路，丢包时各自减半——占带宽多的流掉得最狠，几轮之后大家趋同。AIMD 的「加性增、乘性减」在数学上被证明会收敛到公平分配。换句话说，互联网没有中央交通局，秩序全靠每张网卡自觉执行同一套算法。

BBR 的一句话本质：传统算法把「丢包」当「拥塞」（WiFi 下丢包只是无线干扰，根本不拥塞）；BBR 直接测量瓶颈带宽 × 最小 RTT——这条乘积就是链路真正的容量。代价是公平性争议：BBR 流会挤压 CUBIC 流。

04第四章

封装：洋葱式的四层信封

你的「你好」发出去之前被套了四层信封：HTTP 套进 TCP、TCP 套进 IP、IP 套进以太网帧——每层只管拆自己那层。

分层的意义是各管一段：应用层管「说什么」，传输层管「可靠送达」，网络层管「走哪条路」，链路层管「这一跳怎么过」。收信方按相反顺序拆信封，每拆一层，就多知道一件事该交给谁。

MSS 1460 = MTU 1500 − IP 头 20 − TCP 头 20。你的 12.4KB HTML 会被切成 ⌈12.4KB / 1460⌉ = 9 个段——每段独立编序号、独立确认。若中间某条链路 MTU 只有 1492（PPPoE），路由器要么分片（IP 头里 DF 标志禁止时分片，允许时拆成多片、任一片丢则整包重传）要么回 ICMP「需要分片」——PMTUD 黑洞是 VPN 用户「能连但打不开网页」的经典病因。

再算一笔头部税：1460B 载荷配 54B 开销，效率 96%——很健康。但发一个 41 字节的 TCP 纯 ACK（无载荷），开销占比 132%。小包的头部税远重于大包，这就是 Nagle 算法（攒小包合并发）与它和延迟敏感场景冲突（TCP_NODELAY）永恒拉扯的原因。

06第六章

TLS：握手之后，世界只剩密文

HTTPS = HTTP over TLS。TLS 握手是「在不安全信道上商量出一把只有双方知道的钥匙」——而这一步本身必须是明文的，所以每一帧谁可见、谁不可见，都有明确边界。

逐步走一遍 TLS 1.3 握手，右边同步显示「窃听者视角」：他能看到域名（SNI 明文）、证书链、握手时长——但看不到路径、Cookie、正文。一个常被忽视的细节：SNI（服务器名称指示）在 ClientHello 里是明文的，这正是 ECH（Encrypted Client Hello）要修的最后一个明文缺口。

三个进阶概念值得拥有：①前向保密——ECDHE 每次握手生成全新临时密钥对，就算服务器私钥明天泄露，历史流量也解不开（RSA 密钥交换没有这个性质，所以已被 TLS 1.3 移除）；②会话复用——Session Ticket 让老客免握手直达 0-RTT 发数据，代价是重放攻击面，只该用于幂等请求；③1.2 与 1.3 的 RTT 差——1.2 要 2-RTT，1.3 把密钥交换参数直接塞进 ClientHello 压到 1-RTT。跨洋连接上这就是省 200ms——协议版本本身就是性能优化。

还有一个运维层的真相：TLS 握手的 CPU 开销（非对称加密）约是单次 HTTP 请求的 10 倍，所以高流量站点必须做会话票据复用，否则握手 CPU 就成了瓶颈——Cloudflare 公开过他们每秒百万次握手的优化笔记。

07第七章

HTTP/2：一条马路，多车道复用

HTTP/1.1 一个连接一次只能跑一个请求——前面慢了，后面全堵着。HTTP/2 把报文切成帧，多个流在一条连接上交错传输。

让 CSS2 慢 3 秒试试：HTTP/1.1 的连接 2 上，排在它后面的 JS 只能干等（队头阻塞）；HTTP/2 里 CSS2 的帧稀疏插入，其他流的帧照常穿行。代价是 TCP 层的丢包仍然阻塞所有流——所以 QUIC 干脆把可靠传输也重做了。

HTTP/2 还有一堆「没那么成功的遗产」值得记住：服务器推送被证明几乎没用（推什么由服务器猜，猜错就是浪费带宽），Chrome 在 2022 年移除了它；HPACK 头压缩用静态表 + 动态表把每次重复的 Cookie/UA 从几 KB 压到几十字节——这个倒是实实在在活了下来。技术的演进不是每一个 feature 都值得学习，有些 feature 的价值就是「被验证走不通」。

而下一站 QUIC（HTTP/3）把整个传输层搬进了 UDP：连接 ID 让 WiFi→蜂窝切换不断线、0-RTT 恢复会话、流之间真正独立的丢包重传。它的普及率正以每年 10 个百分点的速度爬升——你读这篇的浏览器很可能已经在用了。

05第五章

HTTP：请求、应答与缓存协商

连接建好，浏览器发请求，服务器给应答。请求行、状态行、头部、正文——每个字段都在说话。

选一个状态码，看服务器怎么答、浏览器接着做什么。301 和 404 的区别不只是数字：301 会触发浏览器再发一次请求（去新地址），404 只是展示错误页——重定向是有成本的，每 301 一次就是一次额外的完整往返。

再往上一层是 CDN：它就是布置在全球几百个节点的共享缓存层，边缘节点未命中才回源。静态资源上 CDN 后，TTFB 从跨洋 150ms 缩到同省 15ms——一个 header 配置的收益超过任何代码优化。

08第八章

路由：每一跳都在减一

从你家路由器到太平洋对岸的服务器，一个包要经过十几台路由器。每台路由器做同一件事：看一眼目标 IP，查表选下一跳，TTL 减一。

TTL（生存时间）是 IP 头里的一个小计数器，发包时设为 64，每过一台路由器减一，减到 0 就地丢弃——没有它，一个配置错误的包会在网络里永远打转。traceroute 正是利用这个机制：故意发 TTL=1、2、3… 的包，逼每台路由器「自报家门」。

但 traceroute 的输出里有大量「假象」需要解读：某跳全是 * * * 不一定是故障——很多核心路由器对 ICMP TTL 超时做了限速（甚至完全不回），流量照常通过；某些跳的延迟突然变小也不是时光倒流——各跳回包走的不同路径，RTT 本来就不能逐跳相加。读 traceroute 是读趋势，不是读绝对值。

而「路由表是谁写的」这个问题指向互联网的另一个层：BGP（边界网关协议）。自治系统（AS）之间用 BGP 互相广播「我能到达这些网段」，全球几十万条路由公告构成的这张表，就是互联网的骨架。2021 年 Facebook 断网 6 小时的直接原因就是一次 BGP 回收——把自家路由撤了，全球 DNS 都找不到它。网络层的「DNS 挂了」往往其实是「BGP 挂了」。

09第九章

速查卡：按下回车后的八件事

如果只带走八句——

① 名字要先变数字

DNS 走完要几十到几百 ms——第一次访问网站慢，一大半慢在这里。

② 握手两次才开谈

TCP 三次握手 + HTTPS 的 TLS 握手——新连接有固定门槛，所以连接要复用。

③ 四层信封各管一段

应用说什么、传输保到达、网络选路径、链路过一跳。排障就是问「哪层出的错」。

④ 状态码是行动指令

200 收货、301 再来一次、304 用缓存、404 认错、500 服务器自己扛——每个码都有后续动作。

⑤ TTL 防永生包

每跳减一、归零即弃。traceroute 用它逼路由器自报家门。

⑥ 延迟大头是物理

光速 × 光纤折射率 ≈ 200km/ms——跨洋 100ms+ 是物理定律，代码优化省不出来。

⑦ cwnd 是驯出来的，不是设出来的

慢启动翻倍、AIMD 线性爬、丢包就减半——互联网的秩序全靠每张网卡自觉执行同一套算法。

⑧ 缓存是最大的性能杠杆

304 的价值不是「快」，是「根本没下载」——正确配置 max-age + ETag 的收益超过任何代码优化。
